# 自动更新与版本管理方案

| 项目 | 内容 |
|---|---|
| 文档版本 | 1.2 |
| 文档状态 | 设计基线（未实现） |
| 更新日期 | 2026年9月29日 |
| 适用范围 | Windows 单文件 EXE（`LLM-Switch.exe`），托盘常驻 |

## 1. 目标

让 EXE 自己完成版本检查与升级，用户不手动下载。方案由两部分组成：程序内的更新流程，以及支撑该流程的版本号规范。

范围限定为最小可用：查版本、下载、校验、替换、重启。代码签名、镜像切换、灰度、增量更新、多平台、自动静默安装均不在本期。

## 2. 更新流程

| 步骤 | 动作 |
|---|---|
| 1 检查 | 启动后延迟 30 秒异步 `GET latest.json`，与当前版本比较。`dev` 版本跳过检查 |
| 2 提示 | 有更高版本时，设置页与托盘标记「发现新版本」 |
| 3 下载 | 下载到 `%USERPROFILE%\.llm-switch\update\LLM-Switch.exe.new`，失败即重下，不做断点续传 |
| 4 校验 | 比对 `latest.json` 中的 `sha256`，不匹配则删除文件并报错，不进入替换 |
| 5 替换 | 启动 `.new` 进程执行替换，旧进程退出后由它完成改名与重启 |

替换细节：

1. 主进程以参数 `--apply-update --wait-pid <PID> --target <原路径>` 拉起下载好的 `.new`。
2. `.new` 进程等待旧进程退出，将原文件改名为 `LLM-Switch.exe.old`，再把 `.new` 改名到目标路径。
3. `.new` 进程按原启动参数（去掉更新参数）重启目标 EXE，随后自身退出。
4. 新版本启动成功后删除 `.old`；启动失败保留，可人工用其回退。

## 3. 关键约束

- Windows 下运行中的 EXE 被锁定，不能覆盖自身，替换必须由第二个进程完成。
- `--apply-update` 分支必须在 `instance.Acquire()` 之前处理。否则新进程可能拿不到单实例锁，或被判定为「已有实例」而只打开管理页。
- 重启保留原参数（`--silent` / `--no-tray`），否则开机启动场景会弹出窗口。
- 替换会中断代理，因此只由用户显式点击触发；下载与校验阶段代理照常运行。
- 单实例锁在旧进程退出后释放，替换流程不得并发执行。

## 4. 更新源

一个静态 JSON，放在 GitHub Releases 资产中，随版本发布：

```json
{
  "version": "0.7.0",
  "url": "https://github.com/xkcyy/llm-switch/releases/download/v0.7.0/LLM-Switch.exe",
  "sha256": "…",
  "notes": "本次更新内容"
}
```

- 只走 HTTPS。
- 检查地址可配置，便于日后换镜像。
- 一次请求拿全版本、地址、校验值与说明，不依赖 GitHub API。

## 5. 接口与配置

| 接口 | 用途 |
|---|---|
| `GET /api/update` | 当前版本、最新版本、更新说明、状态 |
| `POST /api/update/check` | 立即检查 |
| `POST /api/update/download` | 下载并校验 |
| `POST /api/update/apply` | 替换并重启 |

状态取值：`idle` / `checking` / `available` / `downloading` / `ready` / `error`。

配置新增 `Settings.Update`：`auto_check`（默认开启）、`source_url`。只自动检查，不自动安装。

管理面令牌鉴权覆盖以上接口。

## 6. 界面与交互

- 设置页新增「关于」卡片：当前版本、检查更新按钮、状态与更新说明、「重启并更新」。
- 托盘菜单：已发现新版本时为「重启并更新 vX.Y.Z」，否则为「检查更新」。
- 检查与下载显示进度或状态文本；失败给出明确原因（网络错误、校验失败）。
- 升级不可回退到旧版配置时不静默执行，需用户确认。

## 7. 版本管理规范

### 7.1 唯一来源

Git tag `vMAJOR.MINOR.PATCH` 是版本号的唯一来源。`build.ps1` 默认值、`web/package.json`、文档中的版本描述都不是来源，只是产物或说明，不得与 tag 冲突。

### 7.2 语义

| 变更 | 版本位 |
|---|---|
| `config.json` 结构不兼容，或接入配置写入格式破坏性变更 | MAJOR |
| 新增功能、新供应商、新协议、新增可选配置字段 | MINOR |
| 缺陷修复 | PATCH |

非 `vX.Y.Z` 形式的标签不参与更新检查，预发布版本忽略。

### 7.3 构建规则

`build.ps1` 改造后：

1. 默认版本取自 `git describe --tags --exact-match`，`v0.7.0` 归一化为 `0.7.0`。
2. `-Version` 仅用于本地开发构建（`dev` 或 `x.y.z-dev`）。
3. 发版构建前置校验：工作区干净、HEAD 正好在 tag 上、tag 格式合法，任一不满足即失败。
4. 版本经 `-ldflags "-X main.version=…"` 注入，沿用现有链路：`main.version` → `buildinfo.Version` → `GET /api/overview` 与上游 User-Agent。
5. 构建后产出 `LLM-Switch.exe`、`SHA256SUMS`、`latest.json`（版本、地址、校验值、更新说明来自 tag 与变更记录），一并上传 Release。

### 7.4 运行时规则

- 更新检查只信 `buildinfo.Version`；其值为 `dev` 时关闭检查。
- 用 semver 比较，等于或低于当前版本不提示。
- `config.json` 的 `schema_version` 与 MAJOR 联动，MAJOR 变更必须同时提供迁移。

### 7.5 现有偏差

| 位置 | 现状 | 处理 |
|---|---|---|
| `build.ps1` | 默认版本硬编码 0.6.0 | 改为取自 git tag |
| `web/package.json` | 版本 0.2.0 | 不作为来源；界面版本改为读取 `/api/overview` |
| `README.md` / `docs/README.md` | 示例 0.4.2、「适用版本 0.4.x」 | 改为引用 tag 或去掉版本号 |
| `dist/LLM-Switch.exe` | 二进制提交进版本库 | 已定：产物走 GitHub Releases，仓库不再跟踪 EXE（`git rm --cached dist/LLM-Switch.exe`） |

### 7.6 版本号的三个层级

| 层级 | 取值来源 | 是否入库 | 用途 |
|---|---|---|---|
| 发布版本 | Git tag `vX.Y.Z` | 是（tag 本身） | 产物内嵌版本、`latest.json`、更新比较 |
| 开发版本 | `git describe --tags --always` 自动派生 | 否 | 开发构建、日志 |
| 构建号 | `git rev-list --count HEAD` 自动派生 | 否 | 可选，日志与托盘显示 |

人工只做「打 tag」一个动作，其余全部由工具派生。禁止手填版本号，禁止维护版本计数器文件。

构建号用于区分同一发布版本下的不同构建，不参与更新比较。也可引入 goreleaser 自动产出 Release、校验文件与发布说明；当前单 EXE + PowerShell 脚本已够用，不引入新工具链。

### 7.7 分支与提交约束

- 分支名不承载版本。主分支为 `main`，功能分支用 `codex/<slug>`。
- 发版在 `main` 上打 tag，不需要先建版本分支。
- 需要给旧版本单独打补丁时，从对应 tag 切出维护分支 `release/X.Y`（如 `git branch release/0.6 v0.6.0`）。分支名用次版本线，不用精确版本号；补丁修复须合回 `main`，否则下次发版会丢。
- 发布分支可省。只有确实需要维护旧版本时才建。
- 日常提交不强制走脚本。用 `.githooks/commit-msg` 校验提交信息格式，通过 `core.hooksPath=.githooks` 安装。提交信息是下一个版本号的推导输入，因此格式校验从可选变为有必要。
- 发版走唯一入口 `scripts/release.ps1`：代码与变更记录先提交，脚本要求工作区干净；随后 fetch tags、校验分支、按 tag 之后的提交推导版本号、校验变更记录含该版本、跑 `go test ./...`、打 tag、推送分支与 tag。tag 触发 CI（`.github/workflows/release.yml`）执行 `build.ps1 -Release`，产出 EXE、`SHA256SUMS`、`latest.json` 并创建 Release。
- `build.ps1` 不手填版本：HEAD 在 tag 上取 tag，否则取 `X.Y.Z-dev.N+g<sha>`。`-Release` 有三道闸门：工作区干净、HEAD 在 tag 上、产物内嵌版本等于 tag。
- 强制闸门放在 CI 或发布流程，不依赖本地 hook。hook 可被 `--no-verify` 跳过，且不会随 clone 自动生效；CI 校验「产物内嵌版本 == tag」才是有效约束。
- CI 切出代码必须 `fetch-depth: 0`，否则 tag 不在本地，`git describe` 与版本推导全部失败；本地新增 tag 后先 `git fetch --tags` 再推导。

### 7.8 下一个版本号的推导

当前版本取 `git describe --tags --abbrev=0`；仓库无 tag 时以 `0.1.0` 为起点。下一个版本由发版脚本按该 tag 之后的提交推导：

| tag 之后的提交 | 递增位 |
|---|---|
| 含 `!` 或 `BREAKING CHANGE` | MAJOR |
| 含 `feat` | MINOR |
| 其余（`fix` / `docs` / `chore` …） | PATCH |

- 脚本默认打印「当前 0.6.0 → 建议 0.7.0（feat ×3，fix ×5）」并要求确认。
- `-Bump major|minor|patch` 覆盖建议；`-Version X.Y.Z` 直接指定，用于建议不合适的场景。
- 只看 tag 之后到 HEAD 的提交，推荐值必然高于或等于已有最高 tag，不会回退或复用。
- 提交信息不规范时无法归类，脚本退化为 PATCH 并提示显式指定。

### 7.9 不采用的做法

- 维护版本号计数器文件：跨分支不单调、易冲突、易忘记提交。
- 每个功能提交递增版本号：无意义，且必然制造合并冲突。
- 强制所有提交经脚本包装：Agent、IDE、git CLI 都能绕过，只增加摩擦。脚本只管发版。
- 把版本号写进分支名并当作来源。

## 8. 实施步骤

1. 已完成：`build.ps1` 从 tag 取版本并输出 `SHA256SUMS` / `latest.json`；`scripts/release.ps1` 与 `.github/workflows/release.yml` 落地发版流程。
2. 新增 `internal/update`：check、download、verify、apply，含单元测试。
3. `cmd/llm-switch/main.go` 增加 `--apply-update` 分支，位置在 `instance.Acquire()` 之前。
4. `internal/app` 启动后延迟检查；退出前落盘更新状态。
5. `internal/admin` 增加 4 个接口，`Settings` 增加 2 个字段。
6. `web/src/pages/Settings.jsx` 增加「关于」卡片；`internal/tray` 增加菜单项。

后续可选：失败自动回退、检查间隔限频（如 24 小时）、无在途请求时才允许替换。

## 9. 验收标准

- `dev` 构建不发起更新检查。
- 版本相同不提示，版本更高才提示。
- SHA256 不匹配时拒绝安装并清理下载文件。
- 替换后进程正常重启，`--version` 返回新版本；`--silent` 场景不弹窗。
- 新旧进程交替期间单实例锁不误判。
- 替换被中断时旧 EXE 完好，或可由 `.old` 恢复。
- 工作区不干净或未打 tag 时，发版构建拒绝执行。

## 10. 明确不做

代码签名与验签、镜像切换、灰度发布、增量更新、多平台、自动静默安装、双目录版本化。
