# 变更记录

按主题记录产品与实现的演进。版本号为构建时注入到 EXE 的版本（`--version` 可查）。

## 2026-09-25

### 图片输入（0.6.0）

接入 Codex 后无法粘贴截图，原因有两层，各自独立成缺口：

1. **准入层**：Codex 按模型清单的 `input_modalities` 硬拦截，未声明 `image` 时提示「模型不支持图片输入」，图片根本不会发出。此前目录生成只在能力含 `vision` 时写 `image`，而界面没有设置视觉能力的入口，`capabilities` 恒为 `["tools"]`，因此 18 个模型全部是纯文本。
2. **转换层**：即使声明了视觉能力，转换路径也会丢图——IR 没有图片字段，`textOf()` 只取文本，非文本内容块被静默丢弃。只有上游协议为 `responses` 的直通不受影响。

修复：

- IR 增加图片（`irImage`：URL + detail），解码与编码都按「文本在前、图片按序在后」保序。
- Responses `input_image`、Chat `image_url`（字符串或对象写法）、Messages `image`（base64 / URL）三者互转：Responses→Chat 输出 `image_url` 块，Responses→Messages 把 data URI 拆成 `source.base64`，Chat→Responses 输出 `input_image`，Chat→Messages 按 data URI / 远程地址分别输出 base64 或 URL 图片块。
- 无图片时 Chat 的 `content` 仍为纯字符串，请求形态不变。
- 模型编辑弹窗新增「图片输入（视觉）」开关，写入 `capabilities` 的 `vision`；模型列表对已声明的模型显示「图片」标记。能力识别兼容 `vision`/`image`/`multimodal`/`image_input`，大小写不敏感；能力为空或只有 `tools` 视为未知，保持纯文本。

验证：新增 6 个用例——四种转换方向各保留图片、纯图片消息不补空文本块、Codex 目录 `input_modalities` 的有无，另有代理端到端用例断言上游请求体含 data URI。

### 图片能力进入在线元数据补全（0.6.0）

上一节的开关是人工补录，能力本身仍无数据来源。现补齐两条自动来源：

- **上游自述优先**：拉取模型时读取 `/v1/models` 的 `input_modalities`（DeepSeek 等在此自述），声明含 `image` 即写入 `capabilities: ["tools","vision"]`。
- **models.dev 命名空间**：在线元数据新增 `input_modalities` 字段（对应 `modalities.input`）。只在预置类型对应到可信命名空间（deepseek / opencode-go / openai / anthropic）时采信；未知命名空间的全局匹配会命中别家供应商的同名模型，据此声明图片输入会误导 Codex，故不采信。
- 缓存结构加 `version`（当前 2）：旧缓存视为过期触发一次刷新，避免新增字段长期读不到；刷新失败仍继续用旧数据。

覆盖情况（与实测对照）：`ds/deepseek-flash`、`ocg/deepseek-v4.1-flash`、`ocg/glm-5.3-flash`、`ocg/kimi-k2.7-code` 可自动识别；`ocg/glm-5.3` 元数据与实际一致地判为不支持。KmAiModelHub（`km`）在 models.dev 无命名空间、上游也不自述，仍需人工勾选。导入弹窗新增「图片输入」列并显示自动识别数量。

顺带修正导入弹窗「输入窗口/输出窗口」两列的数据键：此前用驼峰键读下划线字段，恒显示「—」。

验证：新增元数据用例（缓存读出模态、旧版本触发刷新并落盘）与能力映射用例；真实拉取 models.dev 核对上述模型。

## 2026-09-23

### 可用模型收为单一出口（内部重构）

「可用模型 = 已启用供应商下的已启用模型，键为 `供应商ID/模型ID`」此前没有名字，判定逻辑在 7 个消费点各写一遍，并已出现口径分歧。现收口到 config 的单一出口：`AvailableModels()` 返回可用模型（含完整供应商与模型定义、slug），`LookupAvailable(slug)` 按请求名取单个，`ModelSlug(供应商ID, 模型ID)` 是请求名格式的唯一来源。定义已写入 `CONTEXT.md`。

改为消费该出口的位置：`/v1/models`、代理路由索引、Codex 模型目录、OpenCode 配置、Trae 接入（模型清单与单模型元数据）、启动自愈的默认模型校验。`admin` 的模型 DTO 与 OpenCode 根级默认模型改用 `ModelSlug`。

行为变化：

- 删除死接口 `GET /api/models/available`（管理界面无调用方；它返回"全部模型 + 启用标记"，是产生口径分歧的两处之一）。将来需要该语义时另加 `AllModels()`。
- 概览的 `enabled_models` 由「只数已启用模型」改为可用模型数：供应商停用时其模型不再计入，与 `/v1/models`、模型目录、接入配置一致。

### 上游请求装配收为一份实现（内部重构，行为不变）

`internal/provider`（连接测试）与 `internal/proxy`（转发）此前各写了一份 `joinURL` 与几乎相同的 `applyAuth`，`provider` 还另写了一份协议到路径的映射。现合并到 `internal/upstream`：

- `upstream.URL(base, suffix)` — 上游地址拼接。
- `upstream.SetAuth(req, provider, proto)` — 按供应商配置挂认证头，并补 Messages 的 `anthropic-version`（已显式设置时不覆盖）。
- 协议到上游路径统一用 `protocol.UpstreamPath()`；`provider` 内新增 `parseProtocol` 作字符串到协议值的转换，未知值按 Chat 处理，与合并前的默认分支一致。

有意**未**合并的部分：`provider` 的 `classify`（错误分类文案）与 `proxy` 的 `upstreamErrorSummary`（错误体摘要 + request id）。两者输出与用途不同，合并会改变现有错误提示。

新增 `internal/upstream` 的测试锁定 URL 拼接、四类认证（bearer / 空类型 / 自定义头 / 无 Key）与 `anthropic-version` 的写入与保留行为。转发链路与连接测试的对外行为不变。

### Trae 接入编排与界面驱动之间加 seam（内部重构，行为不变）

接入编排原先直接依赖 CDP 驱动实体 `*Driver`，除真机端到端（`TRAE_E2E=1`）外没有任何测试面，先删后加、逆序补齐、复核结论这些行为无法验证。

现在 `internal/trae` 内定义 `driverAPI` 接口（`EnsureModelsPage` / `ReadCustomModels` / `AddModel` / `DeleteModel` / `Close`），编排的五个方法改为依赖它：生产实现仍是 CDP 驱动，测试用内存实现。真实驱动代码未改动。

新增 `orchestration_test.go`，用内存驱动锁定下列行为：

- 补齐缺失按逆序添加，使最终顺序等于配置顺序（Trae 新加的排最前）。
- 先删多余、再补缺失，两者不交错。
- 已一致时不做任何界面操作，且结论报告顺序已对齐。
- 集合一致但顺序不对时如实提示「顺序未对齐」，不谎报一致。
- 添加失败时如实报告仍缺的数量，不吞错。
- 重新排序会先删掉全部代理模型再逆序重建。
- 逐个处理的结果映射：`added` / `saved_directly` 计入，`exists` 记为 `present`，异常计入 `failed`。

编排的对外行为不变；需要真机验证的仍只有 CDP 驱动本身（`TRAE_E2E=1`）。

### 供应商 / 模型的写入规则收回 config（内部重构，行为不变）

「加/改/删供应商与模型要维持哪些不变量」原先住在 `internal/admin` 的 HTTP 处理函数里（`normalizeProviderID`、`normalizedProtocols`、`validate`、`normAuth`、改 ID 级联、删除级联），与 `config.sanitize` 的读入修复形成两套实现。

现在 `internal/config` 直接提供写入接口，规则进 implementation：

- `ProviderDraft` / `ModelDraft` + `AuthDraft` 是写入输入；`Enabled` / `Extensions` 为 nil 时新建取默认、更新保持原值。
- `NormalizeProviderID`、`AddProvider`、`UpdateProvider`（含改 ID 级联模型归属与默认模型）、`RemoveProvider`（含连带删模型）、`AddModel`（含首个模型设为默认）、`UpdateModel`、`RemoveModel`。
- HTTP 适配器只做输入转换（`providerInput.draft()` / `modelInput.draft()`）与错误映射，四个供应商处理函数与三个模型处理函数各自缩到十行左右。

姿态差异保留：`sanitize` 是「读入已存在数据时尽力修复」，宽容（丢弃非法项并记录）；写入接口严格（非法即报错、整体不落盘）。两者规则相同、姿态不同，因此不合并。

新增行为锁定测试，先固定现状再重构，重构后全部保持通过：

- `internal/admin/server_test.go`：13 个用例覆盖 ID 归一化、由名称推导 ID、七类输入校验的错误原文、协议去重、地址去尾斜杠、密钥脱敏与"留空保留原 Key"、扩展名原样保留、认证头名取自顶层 `header` 字段、改 ID 级联、删除供应商连带删模型、概览与列表口径。
- `internal/config/config_test.go`：6 个用例把同一批规则测在写入接口上（接口即测试面），后续可直接在 config 层验证，不必再起 HTTP。

两处**有意保留**的现状（已由测试锁定，本次不修）：

1. 写入路径的 ID 归一化（`NormalizeProviderID`）保留下划线与点，与启动自愈的 `DeriveProviderID` 不同——同一个名称经两条路径可能得到不同 ID。
2. 删除默认模型所属的供应商后，`Settings.DefaultModel` 仍指向已失效的模型，要等下次启动自愈才修正；期间 Codex / OpenCode 同步各自兜底。

### 修掉上一条记录里的两处已知缺陷（行为变更）

上一节刻意保留、由测试锁定的两处现状，本次修掉。

**一、供应商 ID 只有一条归一化规则。** 原先写入路径（`NormalizeProviderID`）保留下划线与点，启动自愈的 `DeriveProviderID` 把它们转成 `-` 或删除，同一名称经两条路径可能得到不同 ID；而且自愈只补「缺失的 ID」，配置里已有的怪 ID（大写、空格、斜杠）会一直留着，进而污染对外请求名。

现在 `NormalizeProviderID` 是唯一规则：去首尾空白、空格转连字符、只保留 ASCII 字母数字与 `-` `_` `.` 与汉字、转小写。`DeriveProviderID` 删除，由名称推导 ID 也走同一函数（没有可用字符时仍由调用方兜底随机 ID）。启动自愈改为对**每个**供应商 ID 做归一化，并级联模型归属与默认模型（新增 `cascadeProviderID`，写入路径与自愈共用，避免模型被孤儿清理误删）。

**二、默认模型在任何写入后都保持可用。** 原先删除或停用默认模型后，`Settings.DefaultModel` 仍指向已失效的模型，要等下次启动自愈才修正。现在新增 `ensureDefaultModel`（失效即回退到第一个可用模型，无可用模型则清空）与 `defaultModelFallback`，在 `RemoveModel` / `RemoveProvider` / `UpdateModel`（含停用）/ `UpdateProvider`（含停用）后维持该不变量；`sanitize` 复用同一个回退判定。

管理界面同步：删除 / 停用 / 改名可能改动默认模型，前端在 `removeModel` / `removeProvider` / `toggleModel` / `saveModel` / `updateProvider` 之后读回权威值（`refreshDefaultModel`），不再显示已失效的默认模型。

行为变化清单：

- 名称含空格的供应商，自动推导出的 ID 由 `我的供应商` 变为 `我的-供应商`（空格统一转连字符）；含全角标点的名称（如 `KmAiModelHub（企业）`）推导为 `kmaimodelhub企业`，不再保留全角标点。
- 配置里已有的怪 ID（大写、空格、斜杠、全角标点）会在启动自愈时被归一化，并记一条修复提示；该供应商的模型归属与默认模型前缀随之一并更新。
- 删除 / 停用默认模型（或它所属的供应商）后，默认模型立即回退到第一个可用模型，没有可用模型时清空。

`CONTEXT.md` 补充「默认模型」词条，并在「供应商」词条写明 ID 归一化规则。两处修复均有测试覆盖：`TestProviderIDNormalizationIsSingleRule`、`TestSanitizeNormalizesProviderIDAndCascades`、`TestDeleteProviderFixesDefaultModel`、`TestDisableDefaultModelFixesDefaultModel`、`TestWriteKeepsDefaultModelAvailable`。

## 2026-09-22

### Trae SOLO 接入：高级配置与健壮性（0.6.2）

- **填写「高级配置」**：以前添加模型只填了 API 格式 / 请求地址 / 模型 ID / 显示名 / API Key，Trae 里高级配置全空。现在会按 LLM Switch 的模型元数据写入：**上下文窗口（输入）** ← `context_window`、**思考模式=开启** ← `reasoning.levels` 非空、**图片输入** ← 能力标注或测试反推；输出窗口、工具调用轮数、采样参数、模型系列保持 Trae 默认。
- **图片输入用 Trae 自己的测试反推**：连通性测试发的是带图片的请求，纯文本模型必然报「不支持图片输入」。现在遇到这个提示会先把「支持图片输入」改成**不支持**并重试一次——测试随之通过，模型带着正确能力注册（实测 `ocg/glm-5.3` 从「测试失败→直接保存」变成「测试通过」）。
- **删除前先关弹窗**：若界面上还停着「供应商选择」或添加表单，表格会被盖住导致点不到行内删除图标；删除前先关掉浮层并确认仍在模型设置页。
- 核对方式：Trae 本地缓存里 `prompt_max_tokens` / `thinking_enable` / `multimodal` 分别对应上下文窗口 / 思考模式 / 图片输入。

### Trae SOLO 接入：修正与增强（0.6.1）

反馈驱动的一轮修正（都是真机复现后改的）：

- **修掉「删不掉不一致模型」**：根因是扫描竞态——Trae 的设置页先渲染壳、表格数据后到，读早了会得到 0 行，于是「明明有 4 个多余模型」被判成「没有多余的」，同步也会误判。现在要求**连续两次读到的行数一致**才采信（`waitTableRows`），超时且一行都没有则明确报错而不是静默放过。
- **「接入」改为双向对齐**：补齐缺失 + 删除与代理不一致的自定义模型 + 结尾复核并给出一句如实的结论（例如「Trae 现有自定义模型 16 个：本次新增 0、删除 4；已与本地代理一致」）。因此原来的「断开接入」按钮去掉——清理已经包含在接入里。
- **新增「重新排序」**：Trae 的模型列表是「新加的排最前」，要得到「同供应商相邻」的顺序只能重建。该按钮会删掉全部代理模型后**按逆序重新添加**，使最终展示顺序等于代理配置顺序；由于每个模型都会重跑一次连通性测试，慢上游可能要几分钟，界面上有明确提示与确认。实测 16 个模型重建约 6 分钟，最终顺序为 `ds/* → ocg/* → km/*`，完全一致。
- **顺序不匹配会被如实报告**：新增模型后（新模型落在最前面）接入会提示「顺序未对齐，可点重新排序」，而不是假装一切正常。

### Trae SOLO 一键接入（页面版，已真机验证）

在「脚本版」验证通过后，把 Trae 接入做成了产品能力：

- **页面**：新增「接入 Trae SOLO」页——一个「一键接入」按钮 + 一个「断开接入」按钮；扫描差异是内部动作，用户只需要知道点完之后 Trae 的模型与本地代理一致。
- **Go 内置 CDP 驱动**：新增 `internal/cdp`（极简 CDP 客户端：Runtime.evaluate + Input.dispatchMouseEvent/Escape）与 `internal/trae`（路径探测、argv.json 调试端口、界面驱动、任务进度）。只新增 `github.com/gorilla/websocket` 一个依赖，保持单文件 EXE。
- **差异计算**：以 Trae 设置页表格为服务端真值（实测 `state.vscdb` 字节扫描有 11 个假阳性、纯 Go 读 SQLite 代价过大），扫描一次约 4 秒，只对缺失项执行添加。
- **健壮性**（都是真机踩出来的）：
  - 成功判定用「弹窗关闭」+ 列表回读，不信 Toast（Toast 会残留导致误判「下一条已成功」）；
  - 「已存在」判定只看添加弹窗内部（整页扫描会被聊天记录里的「已存在」字样误伤）；
  - 行扫描要求带删除图标，避免把聊天区的 Markdown 表格当成模型行；
  - 连通性测试带图片输入，纯文本模型必然失败 → 自动走官方「直接保存」；
  - Trae 未运行则带调试端口拉起，正在运行但没端口则引导重启（`--configure-argv` 语义内置）。
- **测试**：`internal/trae` 覆盖差异计算与 argv.json 读写；需要真实 Trae 的端到端用例用 `TRAE_E2E=1` 开启（连上 Trae → 打开模型设置页 → 加一个探针模型 → 校验 → 删除）。
- **实测**：16 个模型全部注册；从 Trae 删掉 `ocg/hy4-preview` 后点同步，页面自动补回（走「直接保存」），代理日志出现 `entry=chat model=ocg/hy4-preview … status=404`（上游本身 404，属预期）。

### Trae SOLO 接入（脚本，已真机验证）

起因：希望 TRAE SOLO 也能用上本机代理的模型。原方案（外部给的思路）是「CDP + Playwright 驱动官方 UI 添加自定义模型」，按此做了可行性分析与真机验证，结论可行并修正了若干坑：

- **调试端口可常驻**：`remote-debugging-port` 在 `argv.json` 白名单里，一次写入永久生效（无需每次换快捷方式启动）。
- **接口确认**：自定义模型由服务端注册（应用内协议 `chat/add_custom_model`，另有 `update` / `test_custom_model_connection`），本地 `state.vscdb` 只是缓存；`client_connect = true`，官方文案说明只支持本地环境。
- **三处关键修正**：① 请求地址应填 `http://127.0.0.1:8317/v1`（「完整 URL」默认关闭，Trae 会补 `/chat/completions`）；② 成功判定要用「弹窗关闭」，Toast 会残留导致误判；③ 连通性测试带图片输入，纯文本模型必然失败，需用官方「直接保存」注册。
- **实测证据**：代理日志 `entry=chat model=ds/deepseek-flash … status=200`；显示名与模型 ID 故意写成不同值，确认请求用的是模型 ID。
- **实测结果**：16 个模型全部注册成功（少数连通性测试通过，多数因「测试请求带图片输入」由脚本点官方「直接保存」注册）；再跑 `--dry-run` 输出「全部已存在，无需处理」。
- **交付**：`tools/trae-solo/sync_models.py`（幂等、可 `--dry-run`、可只处理指定模型、失败留截图），分析文档见 `docs/design/Trae-SOLO-接入分析与方案.md`。

### 转换层修复与供应商多协议（0.5.x）

起因：Codex 在 Responses→Chat 链路上报 `An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`。定位为协议转换缺陷，修复并顺手补齐协议选择能力：

- **并行工具调用合并**：`ResponsesToChatRequest` 把连续的 `function_call` / `custom_tool_call` 合并到同一条 assistant 消息，工具结果按 `call_id` 配对并紧跟其后；缺结果补占位、孤立结果丢弃并写入告警。修掉了「Codex 一轮发两个工具调用必然 400」的问题。
- **思考内容回传（DeepSeek/OpenCode Go）**：代理按「供应商 + 模型 + 工具调用 ID」缓存上游 `reasoning_content`（30 分钟），构造带工具的 assistant 消息时回填；冷缓存对已知思考型供应商写空字符串，避免 `The reasoning_content in the thinking mode must be passed back to the API`。
- **自定义工具桥接**：Codex 桌面版声明为 `custom` 的工具（`exec`、`apply_patch` 等自由文本工具）降级为「单 `input` 字符串」函数工具传给 Chat 上游；上游返回同名调用时还原为 `custom_tool_call`（含 `response.custom_tool_call_input.*` 事件）。此前这些条目会被整对静默丢弃。
- **供应商多协议 + 原生直通优先**：`providers[].protocols` 有序多选（`protocol` 保留为兼容字段，恒等于首项）。选择规则确定：入口协议命中即直通（保留 `store`/`include`/`prompt_cache_key`/custom tools 等原生特性）；未命中按顺序转换；都不行则返回明确错误。`models[].protocol` 仍可把个别模型固定为单协议。
- **连接测试按协议探测**：供应商/模型测试按协议列表逐个探测，返回实际可用的协议（界面提示「连接正常 · responses」）。
- **可观测性**：代理记录与日志新增 `upstream`/`converted`/`warnings`，直通与转换可区分；转换降级会告警。
- **文档**：技术设计方案 §9 补充协议选择规则、转换实现约定与限制。

实测验证：用真实 DeepSeek 与 OpenCode Go 复现原 400（含并行调用的历史），合并后仍报 `reasoning_content` 缺失，补回填后 200；三组请求均通过。

### `reasoning_content` 偶发 400 的收尾修复（0.5.1）

现象：修复后仍偶发 `The 'reasoning_content' in the thinking mode must be passed back to the API`（非必现，集中在 OpenCode Go 的 chat 链路）。

诊断（全部实测）：
- 规则是「每个带 `tool_calls` 的 assistant 消息都必须带 `reasoning_content` 字段，缺失即 400，且覆盖历史里的每一组」；DeepSeek 官方接受空串。
- 用出错会话的真实历史重建请求：19/19 组都带字段，重建体重放 3 次全部 200；90+ 次不同形态探测（空串/缺失/混合/真实 session id）也全部 200。
- 同一时间 OpenCode 客户端（直通链路，代理零转换）也被 OCG 拒了 5 次 —— 说明校验来自上游；判断为**部分网关/路由把空串视为未回传**，叠加长会话缓存过期/重启，命中严格路由时偶发。

修复：
- **非空兜底**：缓存未命中时回填 `(reasoning omitted)` 而不是空串（覆盖「部分网关要求非空」）。
- **提高真实值命中率**：TTL 30 分钟 → 6 小时 + 单条 64KB/总量 32MB 上限与顺序淘汰；流式中断也落缓存（顺带修掉「中断时丢弃最后一个未闭合 SSE 块」）；兼容 `delta.reasoning` / `message.reasoning` 别名（OpenRouter 风格）。
- **可观测性**：4xx 记录改为「上游 HTTP 4xx: <错误体摘要>（request id: …）」，记录新增 `session`；此类问题下次可直接定位到上游路由并向供应商报障，不必再回捞 Codex 会话。
- 端到端验证：真实 OpenCode Go + 19 组工具调用的失败历史 + 冷缓存 → 200，记录里可见占位回填告警。

### 上游兼容与预置修正（0.4.x）

- **预置地址按官方文档修正**：DeepSeek 改为 `https://api.deepseek.com`（不带 `/v1`）；OpenCode Go 改为 `https://opencode.ai/zen/go/v1`；OpenAI / Anthropic 保持带 `/v1`。
- **新增预置 KmAiModelHub**：`https://aimodelhub.ai.kmsoft.com.cn/v1`，默认协议 `responses`（实测该地址同时支持 Chat 与 Responses）。
- **上游请求头约定**：统一 `User-Agent: llm-switch/<版本>`；会话标识 `x-opencode-session` 优先透传客户端会话头（含 Codex 的 `session_id`），缺失时用「模型 + 首条用户消息」生成稳定 ID。修复了 OpenCode Go 报 `Request is missing x-opencode-session` 的问题。
- **模型级协议覆盖**：同一网关不同模型可走不同端点（OpenCode Go：GLM/Kimi 走 chat、Qwen/MiniMax 走 messages、Grok/GPT-Luna 走 responses），导入时自动给出建议。
- **Codex 显示名统一**：模型清单的 `display_name` 固定等于 `slug`（`供应商ID/模型ID`），Codex 模型列表与请求名一致，避免同名模型分不清来源。
- **交互修复**：
  - 二次"从上游同步模型"弹窗关不掉：同步按钮加 loading 去重、每次同步用新弹窗实例、loading 提示改为 finally 销毁、导入重复模型逐条跳过并提示。
  - 修改供应商信息后模型列表被清空：供应商 ID 变更时前端同步重写本地模型的归属与请求名，并跟随选中项。
  - 添加模型弹窗过长被遮挡：弹窗主体限高可滚动，底部按钮始终可见。
