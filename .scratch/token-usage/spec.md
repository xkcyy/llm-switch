# 用量统计

**Status:** ready-for-agent

## Problem Statement

接入 Codex / OpenCode / Trae 之后，本机代理承载了全部模型调用，但运行者看不到这些调用花了多少 token、被调用了多少次。用量只散落在各供应商的账单里，无法在一个地方看清总量，也无法定位是哪个供应商、哪个模型、哪个调用方在消耗。

## Solution

代理在本机记录每次调用的用量，按小时与日聚合。管理界面新增「用量」页：时间为 当天（按小时）/ 近 7 天 / 本月 / 近 30 天 / 自定义（跨度超一个月自动按月），分组为 汇总 / 供应商 / 模型，配趋势折线图、占比条与明细表；总览页显示今日用量卡片。用量只取上游上报值，不估算。

## User Stories

1. 作为本机代理的运行者，我想看到累计的调用次数与 token 总数，以便知道代理总共承载了多少消耗。
2. 作为运行者，我想在汇总、供应商、模型三种分组间切换，以便既看总量也能下钻到具体来源。
3. 作为运行者，我想按模型查看用量，以便知道哪个模型最耗 token。
4. 作为运行者，我想按供应商查看用量，以便与各供应商账单对照。
5. 作为运行者，我想按小时查看当天用量，以便定位突增。
6. 作为运行者，我想查看近 7 天用量，以便快速回顾一周。
7. 作为运行者，我想查看本月用量，以便与月度账单对照。
8. 作为运行者，我想查看近 30 天用量，以便观察趋势。
9. 作为运行者，我想选择自定义起止时间，跨度大时自动按月汇总，以便核算任意时间段。
10. 作为运行者，我想用折线图看用量走势，以便一眼读出变化。
11. 作为运行者，我想用占比条看各分组的份额，以便一眼读出结构。
12. 作为运行者，我想在 Token 与调用次数之间切换图表指标，以便从不同角度看消耗。
13. 作为运行者，我想看到输入 / 输出 / 合计三个 token 数，以便理解用量构成。
14. 作为运行者，我想看到缓存命中 token（有则显示），以便判断提示缓存的收益。
15. 作为运行者，我想看到推理 token（有则显示），以便理解思考型模型的消耗。
16. 作为运行者，我想看到成功与失败调用数，以便区分有效消耗。
17. 作为运行者，我想知道有多少调用没有用量数据，以便判断统计覆盖率。
18. 作为运行者，我想在程序重启后仍看到历史用量，以便长期累计。
19. 作为运行者，我想在删除供应商或模型后仍看到它的历史用量，以便回溯。
20. 作为运行者，我想在总览页一眼看到今日用量，以便日常查看。
21. 作为运行者，我想升级后无需额外配置即开始累计，以便零成本启用。

## Implementation Decisions

**采集点（唯一 seam）**：代理响应收口处（协议转换的 `Deliver`）统一采集用量。直通与转换、流式与非流式全部经过它；`Deliver` 的结果携带用量回传给代理调用方，与现有请求记录合并落桶。

**三条采集路径**：

* 转换路径：IR 已携带用量（非流式 `irResponse.InputTokens/OutputTokens`，流式 `irUsage` 事件），无需新解析。
* 直通非流式：解析响应体 `usage`。
* 直通流式：旁路解析 SSE 事件（不改写字节流），取各协议的上报点：Responses `response.completed`、Chat 末块、Messages `message_start` / `message_delta`。

**字段归一化**：上游 usage 字段名不统一，解析需兜底 `input_tokens`/`prompt_tokens`、`output_tokens`/`completion_tokens`，以及缓存命中、缓存写入、推理 token 的多种位置。

**补齐缺失**：chat 直通在客户端未指定时注入 `stream_options.include_usage`（转换路径本就注入）。

**指标（桶内计数）**：`requests`、`ok`、`err`、`input_tokens`、`output_tokens`、`total_tokens`、`cached_tokens`、`cache_write_tokens`、`reasoning_tokens`、`missing_usage`。

**分组键**：`供应商ID`、`模型ID`。用解析后的唯一标识，不用请求别名；桶内记名称快照，改名后旧历史显示旧名。界面提供 汇总 / 供应商 / 模型 三种视角，调用方仍记录但不是分组维度，入口协议与直通/转换也不作分组维度。

**时间**：桶最细为小时。当天按小时；近 7 天、本月、近 30 天按天；自定义跨度超一个月自动按月。都按本地时区切分。

**保留**：小时桶 + 日桶双写。小时桶保留 7 天，界面只开放「当天」按小时；日桶永久。

**调用方**：沿用 User-Agent 粗判（Codex / OpenCode），识别不出记「未知」，Trae 归「其它」。

**存储**：配置目录下 `stats/`，内存聚合 + 定时/退出原子落盘，重启后加载。

**接口**：`GET /api/usage`，接受时间范围与分组参数，返回总量、时间序列与分组明细。

**界面**：新增「用量」页——时间、分组、指标三个切换，趋势折线图、分组占比条与明细表；总览页加「今日用量」卡片。图表自绘 SVG，不引入第三方图表依赖。

**不做**：费用估算。

## Testing Decisions

好测试只验证外部行为：给定上游响应，代理记录出正确的用量桶与聚合结果，不测内部字段与调用顺序。

**Seam**：沿用现有的 `internal/proxy` 端到端测试 seam——`httptest` 模拟上游 + 代理真实转发（见 `internal/proxy/server_test.go`）。这是最高且唯一需要的 seam。

* 采集覆盖：三协议 × 直通/转换 × 流式/非流式，共 12 条路径，各断言得到的用量。
* 缺失与异常：上游不回 usage（`missing_usage` 计数）、上游错误、流中断、客户端取消。
* 字段归一化：`input_tokens` 与 `prompt_tokens` 两种形状、缓存字段的多位置。
* 请求改写：chat 直通未指定 `include_usage` 时被注入，且不改动其它字段。
* 聚合查询：给定时段与分组，返回正确的求和与时间序列。
* 存储：重启后加载、小时桶 7 天清理、原子写不产生半文件。

## Out of Scope

* 费用与金额估算、单价维护、账单对账。
* 入口协议 / 直通·转换作为分组维度。
* 调用方作为界面分组维度（数据仍采集，未在界面暴露）。
* 每次调用的明细持久化与分钟级粒度。
* 局域网 / 多用户维度。
* Trae 的精确调用方识别。

## Further Notes

* 真实上游探测（2026-09-29）：KmAiModelHub、OpenCode Go、DeepSeek 均上报 usage。唯一缺失场景是 KmAiModelHub 的 chat 流式未请求 `include_usage`。
* 探测同时发现 DeepSeek 的 Messages 端点返回 404，与配置声明不符；与本功能无关，另行处理。
* Anthropic Messages 上游未验证（无可用 key），其用量采集列为待验证。
